# Single-Checker Execution Vertical Slice Design

**Status:** Review candidate
**Date:** 2026-09-26
**Repository:** `kefyusuf/uptime-lab`
**Base:** `main@dabab83a087790b7ec59adcffa6e91f2a4a3ee50`
**Scope:** First real Go Control Plane -> Rust Execution Plane -> normalized result -> Go persistence monitoring loop
**Decision state:** Product direction selected by the landed Next Product Scope Reassessment. This document defines design only and does not authorize implementation.

---

## 1. Purpose

The repository can now register and read Monitoring targets through the live Go public transport, but it still performs no uptime checks.

The next product increment must make a registered Monitor produce real execution evidence while preserving the already-accepted runtime ownership model:

~~~text
Go   = product truth, scheduling/coordination, internal/public API semantics, persistence
Rust = bounded network execution and normalization of protocol/transport outcomes
~~~

This design defines the smallest coherent single-checker execution slice.

The target journey is:

~~~text
registered Monitor
  -> Go decides work is due
  -> Rust claims one work item
  -> Rust executes one bounded HTTP/HTTPS probe
  -> Rust submits one normalized result
  -> Go persists one terminal CheckRun
~~~

The public Monitoring contract remains unchanged in this milestone.

---

## 2. Current implementation truth

The current live Go surface is exactly:

~~~text
POST /monitors
GET  /monitors/{monitorId}
GET  /livez
GET  /readyz
~~~

The current durable Monitoring state is exactly:

~~~text
monitoring.monitors
├── id uuid PRIMARY KEY
├── target_url text NOT NULL
└── created_at timestamptz NOT NULL
~~~

Current invariants that this design preserves:

- Go exclusively owns PostgreSQL product state.
- Rust never accesses PostgreSQL.
- Cross-runtime communication is contract-driven.
- API startup never auto-migrates.
- Landed SQL migrations are immutable.
- Canonical Compose publishes no application host ports.
- Public authentication/authorization, CORS, rate limiting, and ingress remain deferred.
- TargetURL registration is syntactic product validation, not execution-safety validation.
- Web remains a placeholder.
- Checker remains a placeholder until the later implementation phase.

---

## 3. Non-goals

This slice does not design or authorize:

- multiple checker instances;
- horizontal work leasing;
- Kafka, RabbitMQ, NATS, Redis queues, or another broker;
- transactional outbox;
- incidents or notifications;
- public status pages;
- accounts, teams, tenancy, or billing;
- browser authentication;
- public host exposure;
- user-configurable check intervals;
- user-configurable retry policy;
- TCP, DNS, TLS-only, ICMP, or arbitrary probe types;
- React implementation;
- public monitor list/update/delete/enable/disable;
- generalized event sourcing or CQRS;
- response-body content assertions;
- private-network monitoring mode.

The milestone proves one safe HTTP/HTTPS execution loop.

## 4. Locked design decisions

### SCX-001 — One checker process, bounded probe concurrency

The milestone supports exactly one logical Checker process in the canonical topology.

The Checker may execute up to:

~~~text
4 concurrent probes
~~~

The bound is fixed for this milestone.

The process must never create unbounded asynchronous work.

Multi-checker ownership, distributed leases, sharding, and worker identity are explicitly deferred.

### SCX-002 — Every registered Monitor participates automatically

There is still no enabled/disabled lifecycle field.

Every persisted Monitor is eligible for checking.

A Monitor with no terminal CheckRun is immediately due.

Existing Monitor rows therefore become due once:

1. the new schema migration is explicitly applied; and
2. the real Checker runtime starts.

No existing `monitoring.monitors` row is rewritten by the migration.

### SCX-003 — The first cadence is fixed and server-owned

The initial cadence is:

~~~text
60 seconds
~~~

Users cannot configure it.

After a terminal CheckRun, the Monitor is next due when:

~~~text
completed_at + 60 seconds <= Go server time
~~~

The cadence applies equally after:

- an HTTP response;
- a normalized probe failure;
- a coordination timeout.

Scheduling truth therefore remains in Go.

### SCX-004 — Go creates every CheckID

Each issued CheckRun receives a server-generated UUID v7:

~~~text
CheckID = UUID v7 generated by Go
~~~

Rust never invents durable work identity.

The CheckID is the correlation identity across:

- claim response;
- Rust logs;
- probe execution;
- result submission;
- Go logs;
- durable CheckRun state.

No separate distributed trace identifier is required by this milestone.

### SCX-005 — Claiming work creates durable pending execution state

Claiming work is a mutation and therefore must not be modeled as GET.

A successful claim atomically:

1. reconciles any expired pending work;
2. selects one due Monitor;
3. creates one pending CheckRun;
4. returns the work description associated with that CheckID.

A pending CheckRun is durable evidence that work was issued.

A lost HTTP claim response may leave an unexecuted pending CheckRun, but it cannot create duplicate durable identity. That pending run eventually expires and is reconciled by Go.

This is accepted for the single-checker milestone.

### SCX-006 — One pending CheckRun per Monitor

The database must mechanically enforce:

~~~text
at most one completed_at IS NULL CheckRun per monitor
~~~

A partial unique index is the preferred invariant.

This prevents overlapping work for the same Monitor even if claim requests are accidentally concurrent.

It is a local data-integrity invariant, not a distributed multi-worker lease design.

### SCX-007 — Execution acceptance window is bounded

A claimed CheckRun receives:

~~~text
issued_at  = Go server time
deadline_at = issued_at + 20 seconds
~~~

The work description instructs Rust to use:

~~~text
probe timeout = 10 seconds
~~~

The remaining time is submission/recovery margin.

A result is accepted only while:

~~~text
Go server time < deadline_at
~~~

If Go observes a pending run at or after its deadline, it terminalizes that run as:

~~~text
worker_timeout
~~~

before another run for the same Monitor may be issued.

A late result for an already terminalized run is rejected.

This is an execution acceptance window, not a horizontally distributed worker lease.

### SCX-008 — Server timestamps are authoritative

Go owns durable wall-clock timestamps:

- issued_at;
- deadline_at;
- completed_at.

Rust does not submit wall-clock timestamps as product truth.

Rust measures probe duration using a monotonic clock and submits only:

~~~text
durationMs
~~~

This avoids cross-container clock skew becoming product state.

### SCX-009 — Work acquisition returns at most one item

The internal work-acquisition operation returns either:

~~~text
one CheckWork
~~~

or:

~~~text
no work
~~~

It never returns an unbounded batch.

The Checker fills available concurrency slots by claiming serially until:

- four probes are active; or
- Go reports no due work.

When no work exists, Go returns 204 and the Checker waits a fixed one second before the next claim attempt.

### SCX-010 — Internal contract has exactly two product operations

The later implementation is authorized to create:

~~~text
contracts/openapi/internal.yaml
~~~

only with these execution operations:

~~~text
POST /internal/checks/claim
PUT  /internal/checks/{checkId}/result
~~~

No other internal product operation is authorized by this design.

The internal contract is not browser-facing and must not be merged into `public.yaml`.

### SCX-011 — Claim request carries no worker identity

The first milestone has one logical Checker process.

Therefore the claim request needs no:

- worker ID;
- hostname identity;
- lease owner token;
- partition key;
- capability advertisement.

The operation has no request body.

A 200 response contains one CheckWork.

A 204 response means no work is currently due. It carries no product payload; the Checker applies the fixed one-second poll delay locally.

### SCX-012 — CheckWork contains only execution-relevant data

The CheckWork contract contains exactly the concepts needed by Rust:

~~~text
checkId
monitorId
targetUrl
timeoutMs
maxRedirects
~~~

Initial fixed values:

~~~text
timeoutMs   = 10000
maxRedirects = 3
~~~

It does not expose:

- database row shape;
- monitor createdAt;
- public API DTOs;
- Go package names;
- scheduler internals;
- persistence version fields.

### SCX-013 — Result submission is idempotent PUT

Result submission uses:

~~~text
PUT /internal/checks/{checkId}/result
~~~

because the CheckID is already assigned by Go and identifies one result resource.

For one CheckID:

- first valid in-window submission terminalizes the pending CheckRun;
- an exact duplicate submission is a successful no-op;
- a different second payload is a conflict;
- a result after worker_timeout is a conflict;
- an unknown CheckID is not found.

The Checker may retry the identical PUT payload after an ambiguous transport failure without creating a second durable result.

### SCX-014 — Rust submits normalized facts, not raw errors

The accepted Rust result kinds are:

~~~text
http_response
dns_error
policy_rejected
timeout
connect_error
tls_error
protocol_error
internal_error
~~~

Go alone may create:

~~~text
worker_timeout
~~~

Rust must never send raw library error strings as contract data.

The result payload contains:

~~~text
kind
durationMs
httpStatus?   # only for http_response
~~~

Rules:

- durationMs is non-negative;
- httpStatus is present only for `http_response`;
- httpStatus is an integer in the HTTP status-code range;
- non-response result kinds have no HTTP status;
- no response body, headers, IP addresses, stack traces, credentials, or library-specific error text cross the contract.

### SCX-015 — HTTP response is an execution fact, not yet product availability policy

A successfully received HTTP response is represented as:

~~~text
kind = http_response
httpStatus = final HTTP status
~~~

Rust does not decide that 2xx means "up" or 5xx means "down".

This milestone deliberately separates:

~~~text
execution fact
~~~

from future:

~~~text
product availability/state policy
~~~

Go persists the fact but does not yet expose a public Monitor status.

### SCX-016 — No automatic probe retry

One CheckRun represents one probe attempt.

Rust does not automatically retry DNS, connect, TLS, timeout, or HTTP outcomes within the same CheckID.

Automatic probe retries would blur scheduling/result semantics and are deferred.

Only idempotent result-submission transport retry is allowed.

### SCX-017 — Internal HTTP errors are deterministic and sanitized

The internal adapter must use stable, sanitized errors.

Claim semantics:

~~~text
200  one CheckWork
204  no due work
405  unsupported method
500  unexpected internal failure
~~~

Result semantics:

~~~text
204  first accepted result or exact duplicate
400  malformed checkId / malformed request syntax
404  unknown checkId
409  expired run or conflicting terminal result
415  unsupported media type
422  structurally valid but invalid result
405  unsupported method
500  unexpected internal failure
~~~

Successful JSON responses use `application/json`. Structured internal error responses use sanitized `application/problem+json`. Result submission accepts `application/json` only.

No PostgreSQL, pgx, DNS-library, TLS-library, filesystem, or credential details may cross the internal HTTP boundary.

### SCX-018 — Minimal durable execution model is one new check_runs table

The milestone requires exactly one new Monitoring-owned table:

~~~text
monitoring.check_runs
~~~

No separate monitor_states, schedules, leases, incidents, or history aggregate table is introduced.

The table does not duplicate target_url in this milestone because Monitor targets are immutable. Any future target-mutation capability must revisit CheckRun target snapshot/history semantics before that mutation can land.

Conceptual columns:

~~~text
id            uuid PRIMARY KEY
monitor_id    uuid NOT NULL REFERENCES monitoring.monitors(id)
issued_at     timestamptz NOT NULL
deadline_at   timestamptz NOT NULL
completed_at  timestamptz NULL
result_kind   text NULL
http_status   integer NULL
duration_ms   integer NULL
~~~

A new additive SQL migration is required later.

The existing landed migration remains byte-identical.

### SCX-019 — Pending and terminal row shapes are mechanically constrained

The later migration must enforce coherent row state.

Pending row:

~~~text
completed_at IS NULL
result_kind  IS NULL
http_status  IS NULL
duration_ms  IS NULL
~~~

Terminal HTTP response:

~~~text
completed_at IS NOT NULL
result_kind  = 'http_response'
http_status  BETWEEN 100 AND 599
duration_ms  >= 0
~~~

Terminal Rust failure:

~~~text
completed_at IS NOT NULL
result_kind IN (
  'dns_error',
  'policy_rejected',
  'timeout',
  'connect_error',
  'tls_error',
  'protocol_error',
  'internal_error'
)
http_status IS NULL
duration_ms >= 0
~~~

Go coordination timeout:

~~~text
completed_at IS NOT NULL
result_kind = 'worker_timeout'
http_status IS NULL
duration_ms IS NULL
~~~

The table must also enforce:

~~~text
deadline_at > issued_at
completed_at >= issued_at when completed_at is present
~~~

### SCX-020 — CheckRun persistence is append-oriented except terminalization

A CheckRun is inserted once as pending.

The only normal mutation is:

~~~text
pending -> terminal
~~~

A terminal CheckRun is immutable.

There is no update of historical result fields after terminalization.

Exact duplicate result submission returns success without rewriting the row.

### SCX-021 — Due-work selection is deterministic and fair enough for one checker

Go computes:

~~~text
dueBefore = now - 60 seconds
~~~

A Monitor is due when:

- it has no CheckRun; or
- its latest terminal CheckRun completed at or before dueBefore;

and it has no pending CheckRun.

When multiple Monitors are due, selection orders by the oldest scheduling point first, with MonitorID as a deterministic tie-breaker.

The persistence implementation may use PostgreSQL row locking / `SKIP LOCKED` to keep the atomic claim operation race-safe.

Using database locking here does not authorize multi-checker semantics.

### SCX-022 — Expired pending work is reconciled before new work

Before a Monitor can receive new work, any pending CheckRun whose deadline has passed is terminalized as `worker_timeout`.

That terminalization uses the stored deadline as the logical timeout completion instant.

The next 60-second cadence is measured from that terminal instant.

This avoids hot-loop reissuance when a Checker repeatedly crashes.

### SCX-023 — Public OpenAPI remains byte-identical

This milestone does not change:

~~~text
contracts/openapi/public.yaml
~~~

The live public operations remain exactly:

~~~text
POST /monitors
GET  /monitors/{monitorId}
~~~

CheckRun history/current status is not public yet.

After the execution slice lands, a separate product reassessment decides whether the next increment should expose current status, history, or both.

### SCX-024 — Internal transport remains container-internal

The internal Checker operations are served by the Go process on the existing container network.

This milestone adds no host application port and no internet ingress.

There is no new application-level auth/authz mechanism for the internal contract in this local-development milestone.

This is acceptable only because:

- canonical Compose does not publish the API to the host;
- the project is not production-deployed;
- the internal contract is not represented as a public endpoint.

A future deployment/exposure design must revisit service authentication and network policy.

### SCX-025 — cmd/api remains the cross-module composition root

The generic platform HTTP server must remain Monitoring-independent.

Production composition belongs in `cmd/api`.

The implementation may compose a product router that delegates:

- public Monitoring transport;
- internal Checker transport;

while platform-owned `/livez` and `/readyz` retain precedence.

The internal Checker HTTP adapter must not import:

- postgres adapter packages;
- pgx;
- goose;
- platform packages.

It depends inward on narrow Monitoring application interfaces.

### SCX-026 — Rust uses the committed Ports and Adapters shape

The real Checker runtime should follow the previously committed conceptual workspace:

~~~text
apps/checker/
├── Cargo.toml
├── Cargo.lock
└── crates/
    ├── checker-core/
    ├── probe-http/
    ├── control-plane-client/
    └── checker/
~~~

Responsibilities:

- `checker-core`: execution orchestration and contract-neutral result types;
- `probe-http`: safe HTTP/HTTPS execution;
- `control-plane-client`: internal HTTP mapping;
- `checker`: config, wiring, lifecycle, concurrency bound.

HTTP client library types must not leak into checker-core.

### SCX-027 — Production SSRF policy is deny-by-default for non-public destinations

Before any connection, Rust must resolve and validate the destination.

Production policy rejects at least:

- unspecified addresses;
- loopback;
- RFC1918/private IPv4;
- IPv4 link-local;
- IPv6 link-local;
- IPv6 unique-local;
- multicast;
- broadcast where applicable;
- reserved/non-global address ranges;
- documentation/benchmark ranges;
- cloud metadata/link-local endpoints.

An IP-literal target is validated directly by the same address policy without DNS resolution.

A hostname is rejected if its validated resolution set contains any forbidden address.

A permitted connection must use only the exact validated resolution set rather than silently re-resolving the hostname during connect.

This binds validation to the actual connection decision and reduces DNS rebinding risk.

### SCX-028 — Redirects are revalidated as new trust decisions

Redirect following is allowed up to:

~~~text
3 redirects
~~~

Every redirect target must independently pass:

1. supported scheme validation;
2. port policy;
3. DNS resolution;
4. address-range policy;
5. connection-time validated-address binding.

A forbidden redirect produces:

~~~text
policy_rejected
~~~

No redirect target inherits trust from the original URL.

### SCX-029 — Initial target port policy is intentionally narrow

The first execution slice permits only scheme-default ports:

~~~text
http  -> 80
https -> 443
~~~

An explicit non-default port is a valid registered TargetURL but is rejected at execution time as:

~~~text
policy_rejected
~~~

This preserves the existing separation:

~~~text
registration syntax validity != execution safety policy
~~~

Support for alternate public ports requires a later explicit security/product decision.

### SCX-030 — HTTPS verification cannot be disabled

HTTPS probes must perform ordinary certificate-chain and hostname verification.

There is no:

- insecure mode;
- skip-verify flag;
- custom user CA configuration;
- client certificate support;

in this milestone.

TLS validation failure normalizes to:

~~~text
tls_error
~~~

### SCX-031 — Probe resource budgets are fixed

Initial fixed production budgets:

~~~text
max concurrent probes = 4
overall probe timeout = 10 seconds
max redirects         = 3
response body bytes   = 0 application-consumed bytes
response headers      = bounded to 64 KiB total
~~~

The Checker issues GET requests.

After final response headers are available, the response body is not read, buffered, inspected, or persisted.

The implementation must configure the chosen HTTP stack so response-header processing cannot grow without bound.

No response decompression/content parsing is required.

### SCX-032 — Probe duration is measured to terminal execution outcome

For `http_response`, duration measures from probe start until final response headers are received after redirect handling.

For failure results, duration measures until the terminal failure classification.

The measurement uses a monotonic clock.

### SCX-033 — Successful local HTTP mechanics and production SSRF policy require separate evidence

A strict production SSRF policy correctly rejects Docker-internal RFC1918 addresses.

Therefore canonical Docker Compose cannot honestly use another local service as a successful production-policy probe target.

The verification model is layered:

#### Rust probe integration evidence

Successful HTTP/HTTPS mechanics use controlled local test servers with a **test-only injected network policy** that permits only the test server address.

This test-only policy exists only in test code.

The production Checker binary must have no environment variable, CLI flag, or configuration escape hatch that enables private-address probing.

Probe integration tests cover at least:

- successful HTTP response;
- redirect success within limit;
- redirect limit exceeded;
- timeout;
- DNS normalization through controlled resolver fixtures;
- connection failure;
- TLS validation behavior where practical.

#### Production security-policy evidence

Deterministic unit/component tests use synthetic DNS/address fixtures to prove forbidden address classes and redirect revalidation.

#### Real Docker cross-runtime evidence

Canonical Compose uses the real production policy.

The smoke test registers a deliberately Docker-internal target and proves:

~~~text
Go issues work
-> Rust receives it
-> production SSRF policy rejects the private destination before connect
-> Rust submits policy_rejected
-> Go persists the terminal CheckRun
~~~

This is intentionally not misrepresented as a successful network probe.

No external internet endpoint is used by CI.

### SCX-034 — No test-only private-network escape hatch in production

The production Checker configuration schema must not contain:

- allowPrivate;
- disableSsrf;
- insecureTestMode;
- arbitrary CIDR allowlist;
- skipDnsValidation;

or equivalent bypasses.

Test-only network-policy implementations are compiled/referenced from test code only.

This is an architecture-fitness requirement.

### SCX-035 — Checker claim loop is bounded and non-spinning

The Checker execution loop:

1. checks available concurrency slots;
2. claims work serially;
3. starts probes until the four-slot bound is full;
4. when Go returns 204, waits a fixed one second;
5. after a control-plane transport failure, uses bounded backoff rather than a tight loop.

The initial control-plane retry/backoff policy may remain fixed implementation configuration, but it must be bounded and tested.

### SCX-036 — Result submission retry reuses the same canonical payload

If result PUT receives an ambiguous transport failure, the Checker may retry the same payload for the same CheckID.

It must not re-run the probe merely because result submission failed.

A retry must not mutate:

- result kind;
- duration;
- HTTP status.

The exact duplicate semantics in Go make this safe.

### SCX-037 — Checker health proves process readiness, not target reachability

The real Checker replaces the placeholder Checker service but keeps the four-service canonical topology.

Docker health should become true only after:

- Checker configuration is valid;
- runtime dependencies are constructed;
- the worker loop has started.

Checker health does not mean any monitored target is reachable.

Loss of one target or one probe failure must not make the Checker container unhealthy.

The implementation may retain a local readiness marker under the existing `/run/uptime-lab` tmpfs if that remains the smallest deterministic health mechanism.

### SCX-038 — API readiness remains schema-aware and non-migrating

The additive `check_runs` migration becomes part of the repository-owned expected migration set.

Therefore before explicit migration:

~~~text
/livez  -> healthy
/readyz -> unready
~~~

After explicit migration:

~~~text
/readyz -> healthy
~~~

API startup still never applies migrations.

Checker startup remains gated by API health in Compose.

### SCX-039 — No public Monitor state transition yet

Persisting CheckRuns does not add:

- MonitorState;
- up/down status;
- incident transitions;
- availability percentages;
- history endpoints.

Those semantics depend on an explicit later product decision.

This slice stores execution facts only.

### SCX-040 — No new broker/event system

The first Go/Rust loop uses the internal HTTP contract directly.

No broker, event stream, queue service, or outbox is added.

If later requirements demand multi-checker reliable delivery, that decision must be justified by observed workload and a separate architecture gate.

Their exact Go types are implementation details, but dependency direction remains:

~~~text
internal HTTP adapter
       |
       v

       |
       v

       |
~~~

The application layer owns:

The PostgreSQL adapter owns atomic persistence mechanics.

No business policy moves into platform HTTP code.

## 6. Expected atomic claim behavior

Conceptually:

~~~text
BEGIN

1. terminalize expired pending CheckRuns as worker_timeout
2. select oldest due Monitor with no pending CheckRun
3. lock selected candidate safely
4. INSERT pending CheckRun with:
   - CheckID
   - MonitorID
   - issued_at
   - deadline_at
5. return target + work identity

COMMIT
~~~

If no Monitor is due:

~~~text
COMMIT / no mutation
-> 204 No Content
~~~

The implementation plan must require real PostgreSQL concurrency tests for this operation.

Mock-only proof is insufficient.

## 7. Expected result-completion behavior

Conceptually:

~~~text
BEGIN

SELECT CheckRun FOR UPDATE

if not found:
    404

if already terminal and payload == stored canonical payload:
    204 no-op

if already terminal and payload differs:
    409 conflict

if pending and now >= deadline_at:
    terminalize worker_timeout
    409 conflict

if pending and payload valid:
    terminalize with Go completed_at = now
    204

COMMIT
~~~

No raw infrastructure error crosses the application/HTTP boundary.

## 8. Result vocabulary rationale

The normalized vocabulary deliberately keeps protocol facts separate from product availability.

### http_response

The target produced a final HTTP response after safe redirect handling.

The HTTP status is recorded.

### dns_error

Name resolution failed for reasons other than explicit policy rejection.

### policy_rejected

Execution was refused before or during redirect processing because the destination violates the safety policy.

### timeout

The overall probe deadline elapsed.

### connect_error

A safe, validated destination could not be connected to.

### tls_error

HTTPS certificate/hostname/handshake validation failed.

### protocol_error

The remote endpoint produced an HTTP/protocol outcome that could not be treated as a valid HTTP response and was not better represented by another category.

### internal_error

The Checker encountered an unexpected internal condition.

The result remains sanitized. Detailed internal diagnostics stay in Checker logs.

### worker_timeout

Go did not receive a result within the execution acceptance window.

This is generated by Go only.

## 9. Internal contract boundary

The future `contracts/openapi/internal.yaml` is authoritative for Go/Rust HTTP mapping only.

It must not become the source of:

- domain object design;
- database schema design;
- Rust crate-internal types;
- Go storage structs.

Both runtimes map between contract DTOs and their own internal models.

Contract semantic fitness must mechanically enforce:

- exactly two operations;
- no public Monitoring create/read operations copied into internal.yaml;
- required CheckID/MonitorID UUID shapes;
- closed result-kind vocabulary;
- result conditional-field rules where OpenAPI can express them;
- no raw error field;
- no arbitrary map payloads;
- no auth/securitySchemes until a later explicit internal-auth gate.

## 10. Security model

The Checker is the only runtime authorized to perform user-directed outbound network access.

Go must never execute the target URL.

The security order for every initial request and redirect is:

~~~text
parse target
-> scheme check
-> effective port check
-> resolve hostname
-> reject if any resolved address is forbidden
-> bind connection to validated resolution set
-> execute bounded request
-> classify terminal fact
~~~

A redirect repeats the full sequence.

The safety policy is not inferred from a successful initial registration.

~~~text
-> API ready
-> real Checker healthy
-> register Monitor pointing at private Compose address
-> Go creates pending CheckRun
-> Rust claims work
-> Rust production policy rejects private destination before connect
-> Rust PUTs policy_rejected result
-> Go persists terminal CheckRun
-> no pending row remains for that Monitor

-> down -v destroys both
-> explicit migration required again
~~~

CI must inspect persisted CheckRun evidence directly through PostgreSQL because the public API intentionally remains unchanged.

## 15. Failure and recovery semantics

### Checker crashes after claim

The durable CheckRun remains pending.

After deadline, Go terminalizes it as `worker_timeout`.

A later claim can issue new work according to the fixed cadence.

### Claim response is lost

The persisted pending CheckRun eventually becomes `worker_timeout`.

The Checker does not attempt to reconstruct unknown work identity.

### Probe succeeds but result response is lost

The Checker retries the identical PUT.

Go returns 204 for exact duplicate completion.

### Checker submits after deadline

Go rejects the result with 409 after terminalizing/observing `worker_timeout`.

### Go/DB unavailable during claim

No work is executed.

Checker backs off and tries again later.

### Go/DB unavailable during result submission

Checker retries the same result payload within its bounded submission policy.

If it cannot deliver before the server-side acceptance window, the run may eventually become `worker_timeout`.

The probe is not repeated under the same CheckID.

## 16. Alternatives rejected

### A. Cron loop entirely inside Go

Rejected.

It would execute no Rust boundary and would move the project away from the accepted Control Plane / Execution Plane architecture.

### B. Rust reads PostgreSQL for due work

Rejected.

It violates ADR-0003 and turns schema into a hidden cross-runtime API.

### C. Add a broker now

Rejected.

One Checker and direct internal HTTP do not justify broker/outbox operational cost.

### D. Add a durable schedules table

Rejected for this slice.

Fixed cadence can be derived from Monitor creation and CheckRun terminal timestamps.

A separate schedule table becomes justified only when mutable/user-configurable scheduling exists.

### E. Add Monitor enabled/disabled state first

Rejected.

It expands lifecycle semantics without being necessary to prove execution.

### F. Make CheckResult immediately public

Rejected.

It combines execution, product-state policy, and public contract expansion in one milestone.

The next reassessment should decide status/history product semantics after execution facts exist.

### G. Permit private Docker targets in production policy for easier smoke testing

Rejected.

Testing convenience must not create a production SSRF bypass.

### H. Depend on a public internet target in CI

Rejected.

CI must remain deterministic and not rely on third-party availability/network policy.

## 20. Self-review

### Product value

PASS.

The design turns the repository from a target registry into a system capable of executing and durably recording monitoring attempts.

### Runtime ownership

PASS.

Go owns schedule/work/persistence. Rust owns network execution. PostgreSQL remains Go-only.

PASS.

Fixed 60-second cadence avoids premature mutable policy state and removes the need for a separate schedule table.

PASS.

Durable pending CheckRuns plus a bounded acceptance window handle lost claim responses and Checker crashes without introducing distributed leases.

PASS.

Go-assigned CheckID plus idempotent PUT prevents ambiguous result-submission retries from duplicating durable results.

PASS.
