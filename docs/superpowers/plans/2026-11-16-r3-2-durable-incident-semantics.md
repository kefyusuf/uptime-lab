# R3-2 Durable Incident Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Materialize confirmed outages into durable incident open/resolve state on the Go write path, defined separately from the unchanged evidence-derived availability read (R0 incident-separation mandate): N=3 consecutive terminal target-failures open an incident, M=2 consecutive terminal target-successes resolve the open incident, and an inconclusive result resets both counters without resolving. Confirmation becomes unbounded by evidence retention and survives restart. One new bounded public read `GET /monitors/{monitorId}/incidents` exposes durable incident history with the check-run history cursor/budget conventions and a distinct version-3 cursor. One new migration (00005); the availability read, the ten existing operations, the result-kind vocabulary, Rust and the internal contract are unchanged; notification is deferred to R4.

**Architecture:** Go owns a pure incident fold (`domain.ApplyIncidentOutcome` over `IncidentState`), a shared outcome classifier extracted from the R3-1 availability policy (behavior-preserving), two new tables (`monitoring.incident_state` counters + open pointer, `monitoring.incidents` history) added by migration 00005, and a write-path fold inside the existing CheckRun `FOR UPDATE` transaction: `CompleteCheck` folds normal and late-timeout terminalizations, `ClaimDueCheck` reconciliation bulk-resets expired-pending `worker_timeout` outcomes. Incident identity is application-assigned (`SubmitCheckResult` mints a candidate `IncidentID` through `CompleteCheckInput`); `Repository` stays pool-only. A new bounded keyset read (`monitor_incidents.go` `Page`, `opened_at DESC, id DESC`, version-3 cursor) and `GetMonitorIncidents` use case mirror history exactly. Composition grows: `NewModuleWithIncidents`/`NewHandlerWithIncidents` and an incident-id generator in `NewExecutionModule`. The restricted gateway allowlist forwards the new GET. The browser adds a closed incident decoder/model and an incident-history section beside the unchanged `AvailabilityCard`. Availability and incidents are separate projections sharing identical transition semantics over different windows; divergence is documented, never coupled.

**Tech Stack:** Existing Go 1.27.4/pgx/goose, PostgreSQL 18.6-alpine3.24, OpenAPI 3.1.2, Redocly CLI 2.53.3, React/TypeScript/Vitest/Playwright, Node 24.21.0/npm 11.19.1. One new migration (00005); no new dependencies.

## Global Constraints

- Durable incident semantics only: a per-Monitor `incident_state` fold (consecutive failure/success counters plus an open-incident pointer) and distinct `incidents` history rows. No notification (R4), no uptime percentage, no maintenance window, no per-Monitor configurable threshold, no aggregation, no ownership/remote access, no historical backfill. Thresholds reuse the fixed R3-1 domain constants `confirmationFailureThreshold = 3`, `recoverySuccessThreshold = 2` (R0-03 local conventions).
- The availability read is UNCHANGED: `EvaluateAvailability`, `RecentTerminalByMonitorID`, the availability operation/schema/reason enums, the bounded newest-5 window and latest-only future/stale (>120s) precedence all stay exactly as R3-1 landed them. The existing availability suite is the regression guard. Incidents are a separate projection with identical outcome semantics over a durable unbounded window with no freshness rule; the incident read is never derived from the availability assessment.
- Outcome mapping is reused verbatim through a shared classifier extracted from `availability.go` (behavior-preserving refactor): success = `http_response` 2xx; failure = `http_response` non-2xx plus `dns_error`/`timeout`/`connect_error`/`tls_error`/`protocol_error`; inconclusive = `policy_rejected`/`internal_error`/`worker_timeout`. No new result kind.
- Fold hook = every path that actually terminalizes a previously-pending run: `CompleteCheck` normal completion and late `worker_timeout`, plus `ClaimDueCheck` reconciliation's expired-pending bulk inconclusive reset. Idempotent-duplicate, conflict and not-found paths do NOT terminalize and therefore do NOT fold; an idempotent re-delivery never double-counts.
- Fold transitions: inconclusive -> `FailureStreak=0`, `SuccessStreak=0`, open incident unchanged, action none. success -> `FailureStreak=0`, `SuccessStreak++`; if open and `>= M` resolve (`resolvedAt`, `resolvedByCheckId`), clear pointer, `SuccessStreak=0`; else none. failure -> `SuccessStreak=0`, `FailureStreak++`; if not open and `>= N` open(candidateID, `openedAt`, `openingReason`, `openedByCheckId`); else none. A first success with no open incident is none; an already-open incident is never re-opened.
- Serialization: the existing one-pending-per-Monitor partial unique index plus the CheckRun `FOR UPDATE` row lock already serialize per-Monitor terminalizations; the fold reads-modifies-writes `incident_state` inside that same transaction. NO new `monitors` lock in `CompleteCheck` (it would deadlock against `ClaimDueCheck`'s Monitor-then-pending-INSERT order). Lock order is CheckRun -> incident_state -> incidents; only `ClaimDueCheck` then locks `monitors`, with `FOR UPDATE ... SKIP LOCKED` (never waits). Real-PostgreSQL parked-lock + `pg_locks` tracer evidence is required.
- Incident identity is application-assigned: `SubmitCheckResult` mints a candidate `IncidentID` per completion via `ports.CompleteCheckInput.IncidentID`; the adapter consumes it only when the policy opens. `Repository` stays pool-only (`NewRepository(pool)` unchanged). Reconciliation never opens, so it needs no candidate id. State rows accrue lazily from the first completion (zeroed init, no backfill).
- Migration 00005 is additive: `monitoring.incidents` + `monitoring.incident_state`, the `incidents_one_open_per_monitor_idx` partial unique index (`WHERE resolved_at IS NULL`), the `incidents_monitor_opened_idx (monitor_id, opened_at DESC, id DESC)` keyset index, `monitor_id` FKs with no cascade (manual delete sweep), evidence FKs `ON DELETE SET NULL` (retention-safe, DB-enforced, no retention-adapter change), CHECK `resolved_at IS NULL OR resolved_at >= opened_at`, non-negative streak CHECKs, two-reason `opening_reason` CHECK. Down drops `incident_state` then `incidents`. 00001-00004 stay immutable. `migrations.CompatibilityChecker` derives its expected set dynamically from `provider.ListSources()`, so readiness grows four->five (`/readyz` requires goose version 0 plus all five applied); the mechanism is unchanged and no test hardcodes the count.
- Incident read mirrors history: one Read Committed transaction, `pgx.Batch` existence probe + keyset page, binary `pgtype.UUID`, `maxRows` 1..51 (limit+1 lookahead), `ORDER BY opened_at DESC, id DESC`, anchored `(opened_at, id) < ($2, $3)`, probe-first snapshot rule. Monitor absent -> `ports.ErrMonitorNotFound`; present with no incidents -> empty slice (successful empty page). Version-3 cursor `"3|"` rejects inventory (`1|`) and history (`2|`) tokens; 66-char raw -> 88-char unpadded base64url, strict canonical re-encode.
- HTTP incident read mirrors `serveHistory`: exact path match, `ContentLength` 0 / no `TransferEncoding`, 128-byte ASCII query with only `limit`/`cursor` each once (no dup/empty/unknown), limit 1..50 default 20, 245760-byte compact JSON budget (128-byte base overhead, per-item cost plus comma, lookahead-driven `nextCursor`), `Cache-Control: no-store` on every matched response, GET-only else 405 `Allow: GET`, 400 invalid query/UUID, 404 unknown Monitor, sanitized 500. Gateway forwards the new GET through the existing Host/Origin guards; no new mutation route.
- Edit/delete/pause: `EditTarget` does not touch incident state (a streak/incident may span an edit, documented mixing); the deletion batch additionally sweeps `incidents` and `incident_state` (before the lock and again under it, mirroring the CheckRun double-sweep); pause freezes the fold while an open incident persists. Restart resumes from persisted counters; no in-memory state.
- Rust and `contracts/openapi/internal.yaml` unchanged. English code/docs/copy; concise Turkish before/after updates. Record focused RED reason, GREEN result and commit per task. Tool/setup failure is blocked verification, not product RED. Preserve user-owned changes; explicit paths only in commits. Allowed scopes: web, api, checker, contracts, devops, architecture, docs, deps.

## Review Focus

- The fold cannot open below N or resolve below M, and never re-opens an open incident: Task 2 pins N-1/N open boundaries, M-1/M resolve boundaries, immediate first success (no up-transition gate) and no-re-open-while-open; lowering a threshold or re-opening must reproduce a specific failure.
- Inconclusive reset is not bypassed and never resolves: Task 2 pins both counters zeroed with the open pointer unchanged; Task 3 pins late-timeout and reconciliation reset on the real write path. Dropping the reset boundary must fail.
- The shared classifier preserves R3-1 semantics exactly: Task 2 pins classifier parity and keeps the entire existing availability suite green; a behavior-changing extraction must fail the regression guard.
- The write-path fold is idempotent and serialized without a Monitor-lock deadlock: Task 3 pins no re-fold on duplicate/conflict/not-found, the one-open invariant under concurrent completion, unbounded confirmation surviving retention truncation, and a parked-lock `pg_locks` tracer proving CheckRun -> incident_state -> incidents order with no `monitors` wait in `CompleteCheck`.
- Incident identity is application-assigned and the repository stays pool-only: Task 3 pins the candidate `IncidentID` minted by `SubmitCheckResult` and carried through `CompleteCheckInput`, consumed only on open.
- Migration 00005 is additive, reversible and readiness-correct: Task 1 pins up/down, immutable 00001-00004, the one-open partial unique index, evidence FK `ON DELETE SET NULL`, no FK cycle, and the dynamic compatibility checker accepting the five-migration set.
- The incident read cannot over-fetch, mis-map absence or accept a foreign cursor: Task 4 pins the limit/lookahead, `opened_at DESC, id DESC` tie-break, monitor-not-found vs empty page, the keyset index usage, and version-3 canonicality rejecting `1|`/`2|` tokens.
- The new operation is closed and the existing surface is untouched: Task 5 pins the closed `MonitorIncidentPage`/`MonitorIncident` shapes, the two-reason enum, optional evidence omitted when null, and unchanged availability plus all ten existing operations with generated parity.
- Transport guards and the gateway allowlist hold: Task 6 pins `no-store`/`Allow`/`HEAD`/404/400/sanitized-500, query-grammar/cursor/byte-budget rejection, the composed handler serving incidents, and the gateway forwarding only the contracted GET.
- The browser cannot accept a mismatched incident shape or render an unknown reason: Task 7 pins closed decoding (open vs resolved, null evidence links) and the section rendering, with `AvailabilityCard` unchanged.
- Task 8's journey proves sustained failures open a durable incident, sustained successes resolve it, incident history survives an API restart and evidence retention truncation, and the availability read remains the separate evidence-derived assessment, with durable SQL linkage.
